## 2026-10-14（修复轮）
- **重连死锁（本轮最关键）**：`restartSessionWith()` 持 `sessionLifecycleMutex` 调用 `scrcpy.stop()/start()`；而 `stop()/start()` 内部回调 `NativeCoreFacade.onScrcpySessionStopped/Started()`，这两个回调**再取同一把锁** ⇒ 永久互锁：视频消费器已断（画面冻死）、`isRestarting` 卡 true（后续切换全变哑）。**规律：凡"调用方持锁 + 被调方（或其后代调用）回调取同锁"的链路必须全链路审计**。三条重启路径（流转=本次新写；解码错误重启/分辨率降级=上游同款缺陷）已全部改为不持锁；start 失败必须清 `isRestarting` 标志。此类运行时互锁 JVM 单测覆盖不到——真机复测项是唯一护栏。
- **AGP 增量打包孤儿条目**：增量 `assembleDebug` 会在旧 APK 上追加新条目并重写中央目录，旧条目残留为孤儿数据（实测本地条目 1157 vs CD 1098、+2.19MB；解压内容逐字节相同）。**双构建字节对比必须 clean-vs-clean**；交付物取 clean 构建。
- **解锁跳回回弹陷阱**：解锁时若系统直接把 StreamActivity 恢复前台，re-entry 标记会滞留；用户随后退出串流时 MainActivity.onResume 会误判"从外部回来"并回弹 ⇒ StreamActivity.onResume 必须消费 re-entry。
- **接收器生命周期**：解锁类接收器不能绑 Activity 生命周期（MainActivity 可能不在栈上）⇒ 绑会话生命周期（facade 会话起停钩子）。
- BUG3（保活通知）用户撤回：未做任何通知相关改动；不写复测项。

## 2026-10-14（v3 · 画中画移除）
- **PiP 自动进入+无法关闭的组合坑**：androidx.core.pip（1.0.0-alpha04）的 `BasicPictureInPicture.setEnabled(true)` 让 App 在用户离开串流页时**自动进 PiP**；小窗"关闭"动作在国产 ROM 上点不动（接收器文件自带 `// not working in MIUI` 注释）；唯一兜底 `dismissActivePictureInPicture()` 只在 MainActivity 恢复时触发 ⇒ 离开 App 后小窗"无法消除"。**教训：引入系统级 overlay 能力（PiP/悬浮窗）前，先确认关闭路径在所有目标 ROM 上可用，且要有不依赖用户回到本 App 的兜底关闭路径。**
- 删除范围要连"系统级声明"一起删：仅删代码不够——`android:supportsPictureInPicture` 移除后系统才拒绝 PiP（双保险）；依赖项（core-pip）与专属字符串（password_stop_mirroring）同步清理，避免半残留。
- 单测层面无 PiP 用例、虚拟按键目录原本无 PiP 按钮——"删干净"的验证落在：残留扫描（grep 宽口径）+ APK 抽查（classes.dex strings / aapt2 manifest）+ 真机 P11。

## 2026-10-14（v4 · 解锁跳回重做）
- **v2 解锁跳回三宗罪**（按设备日志复盘）：①单触发源——`ACTION_USER_PRESENT` 在该设备整轮零送达（有 keyguard 事件但广播没进接收器）；②注册绑"会话生命周期"——流转重连反复 unregister/register（日志 13:55–13:57 肉眼可见），窗口期必漏；③任务栈——桌面 launcher 以 `flg=0x10200000`（RESET_TASK_IF_NEEDED）重拉 MainActivity 会清掉其上的 StreamActivity，而"回前台过渡"标记被乱序消费 ⇒ 停在设备列表。**教训：系统级行为（解锁/亮屏/任务恢复）的触发面必须多路冗余 + 注册点必须进程级，且不能依赖单一"过渡标记"的时序。**
- **原项目正解（照搬）**：`RecoveryDynamicReceiverRegistrar`（USER_PRESENT/SCREEN_ON/SCREEN_OFF 必须动态注册，targetSdk≥26 隐式广播豁免清单不含它们；挂 Application 进程级载体）+ `MainAutoJumpPlan`（MainActivity.onResume 五判据无条件跳转，"主界面配置后基本用不上"——同一用户当年的强需求口径）。**跨项目移植时优先翻原项目里已在这台设备上验证过的机制，比自创时序方案可靠。**
- **轮询兜底的价值**：广播送达是 ROM 玄学；`isInteractive && !isKeyguardLocked` 的 false→true 跳变轮询是唯一设备无关的触发源（2s 粒度、进程内、零权限）。三路冗余中它最稳。
- BUG2"流转小窗"归因闭环：全仓无窗口创建 API（仅两个应用内表面）⇒ 只可能是系统 PiP（v3 已删）；"无法消除"= 关闭动作在国产 ROM 失效（接收器自带 `// not working in MIUI` 注释）。**症状学：凡是"无法消除的系统级小窗"，先查 PiP/悬浮窗类系统能力，再查渲染层。**

## 2026-10-14（v5 · 流转画面修复 + 锁屏唤醒）
- **流转"无画面"根因=双视频表面争抢解码输出（last-attach-wins）**：全屏控制页与设备卡预览两个 `ScrcpyVideoSurface` 都会在生命周期/重组事件里 attach 到 facade；活动切换/解锁跳转/熄屏亮屏重组时两个表面在 150ms 内 ≥5 次交替互抢（日志 14:35:23），输出绑定到"最后一条消息的赢家"——**与用户在看哪个界面无关**；赢家是被盖住的主界面预览时 ⇒ 全屏黑屏但音频照常（"只有声音没画面"）。修复=双槽位（primary/preview）+ 优先级策略（全屏请求总抢占；预览仅在无可用全屏时生效；detach 全屏回退预览）。**教训：共享单输出（解码器 surface）的多视图架构必须显式定优先级；last-write-wins 在 UI 生命周期抖动下必然翻车。**
- **锁屏唤醒移植的安全设计**：原项目 `ControlledLockWake v3` 的关键是"保守链"——两轮取样、真安全锁拒 dismiss、唤醒未送达拒 dismiss、一切不确定 ⇒ 不动作；vivo 的 `secure=true` 因 `deviceLocked=0/TRUSTED/0x0` 仍授权 dismiss（**"secure 标志"≠"真安全锁"，须看 trust 三字段**）。**移植安全动作类功能时，把"拒动作"判据当主体实现，动作当例外。**
- **目标项目密码能力研究结论**：`EncryptedSharedPreferences`（Keystore 主密钥）+ 生物认证门控的 `InjectionController.injectText`——**不存在全自动注入路径**；自动解锁不绕过该门控（安全边界）。勿把"有密码库"误读为"可自动输入"。
- **工程坑（批量编辑脚本）**：python 暂存/还原行级片段时 `split("\n")[:2]` 丢失行尾换行 ⇒ 还原时把两条语句拼成一行（`import Ximport Y` / `…resetEpisode(...)        controller.releaseAll()`），编译才暴露。**暂存行片段必须保留并校验结尾换行；批量编辑后先编译再提交**（本轮已 amend + force-with-lease 修正，未留坏提交）。
- **工程坑（批量替换计数）**：`attachVideoSurface(surface)` 实际 4 处而非 3 处——**批量替换前先 grep 精确计数**，脚本对 count 断言防呆（本轮脚本因断言拦下错误、避免了半替换）。
